# 总体架构与一致性决策

## 1. 已核实的当前代码事实

本设计以当前工作树为准，而不是假定旧版 QQ 群能力仍不可用。

| 位置 | 已有模式 | 对本次的约束 |
| --- | --- | --- |
| `...api/QQGuildApi.kt` | `Get/Post/Put/Delete/PatchQQGuildApi` 统一构造 `/v2/...` URL；伴生对象继承 `Simple*ApiDescription`。 | 每个新接口都采用私有构造器 + `Factory.create(...)`，不能手写散落的 URL。 |
| `...api/ApiRequests.kt` | `requestData` 自动添加鉴权、检查 HTTP 状态、用 `QQGuild.DefaultJson` 解码；空结果使用 `QQGuildApiWithoutResult`。 | 空 `{}` 或空响应的写操作必须以 `Unit` 建模，不能为它们伪造回执字段。 |
| `...api/panel/*` 与 `model/panel/*` | 近期 v2 能力使用 camelCase 属性、`@SerialName`、公开不可变模型、低层不做业务校验；列表查询由 URL 参数实现。 | 本次 v2 群管理模型按相同风格实现；服务端枚举保留原始 `String` 加常量，避免未知值导致反序列化失败。 |
| `...core/group/QGGroup.kt` | 过去因 API 未开放，`name` 固定空串、`members` 固定空集合、`member` 固定 `null`。 | 只能把已有官方能力接进对应操作；不能让普通属性读取隐式网络查询或加入本地缓存。 |
| `...core/guild/QGGuild.kt` / `QGGuildImpl.kt` | 成员列表是冷 `Collectable`；`member(id)` 是挂起查询；API 模型由 snapshot wrapper 透出 `source`。 | `QGGroup` 的成员查询、成员详情、分页行为应复用该组织方式。 |
| `...core/panel/*` 与 `...core/menu/*` | 与标准 simbot 概念不完全一致的全局资源使用 bot 级 manager、snapshot/handle、内部实现；不缓存远端状态。 | 自动审批策略放在 `QGBot`，不用硬塞进 `ChatGroup` 或 `GroupRelation`。 |
| `module-info.java` 与 root `apiValidation` | API 模块通过 JPMS 精确导出包，并由 binary-compatibility-validator 跟踪公共 API。 | 新 `api.group`、`api.group.approval`、`api.group.member`、`model.group` 必须显式 export；更新 api dump 是交付物而非可选项。 |

本工作树有未跟踪的 `.local/`、`CONTEXT.md`、`patch.patch` 和本地测试文件；本计划不修改它们已有内容。特别是任何本地运行凭证都不应抄进测试、文档或日志。

## 2. 分层与包名

```text
simbot-component-qq-guild-api
└─ love.forte.simbot.qguild
   ├─ model.group
   │  ├─ GroupInfo.kt                 # 群资料、机器人状态
   │  ├─ GroupMember.kt               # 成员、分页、黑名单
   │  ├─ GroupJoinRequest.kt          # 申请、审批、禁言
   │  └─ JoinApprovalStrategy.kt      # 策略及请求/回执
   └─ api.group
      ├─ GetGroupInfoApi.kt ...       # 群路径下的读/写接口
      ├─ approval/                    # /v2/groups/join_approval_strategy
      └─ member/                      # members、batch_remove、member_blacklist

simbot-component-qq-guild-core
└─ love.forte.simbot.component.qguild
   ├─ group/                          # QGGroup 与群/成员/申请 snapshot 公共类型
   ├─ internal/group/                 # 请求委派、分页 flow、snapshot 实现
   ├─ approval/                       # 仅 bot 级的策略 manager、handle、snapshot
   └─ internal/approval/
```

选择 `group`（单数）与现有 `api.message.group` 一致；不能复用频道的 `api.member` 或 `model.Member`，因为 QQ 群的 `member_openid`、角色、禁言和黑名单语义不同。策略资源没有 `group_openid` 路径参数、一次能关联最多 100 个群，因此不属于任何一个 `QGGroup` 的所有物。

## 3. 明确的公共 API 决策

### 3.1 低层 API 是完整镜像，不是业务服务

低层模块必须实现清单中的全部 17 个端点，即使某些端点仍为内邀。`create` 工厂只负责保存调用方给的参数并构造 URL/body；不在本地推断权限、查询群是否存在、截断集合、拆分超过上限的批次，或把 `on/off`、`add/del` 等未知未来值拒绝掉。这样与 `GetCommandPanelListApi` 和 `ModifyCustomMenuApi` 的“服务端决定有效性”保持一致。

例外是类型安全本身：请求体使用 `List<String>` 保存 OpenID/QQ 号码，QQ 号码绝不转 `Long`；策略 `group_ids` 同样使用 `List<String>`，因为官方已说明 uint64 与 JavaScript 精度冲突。`limit` 仍是 `Int?`，因为它是 API 数值查询参数。

### 3.2 原始字符串优先于 Kotlin enum

`member_role`、`recv_msg_setting`、`apply_source`、`verify_info.method`、审批 `op`、禁言 `op/mode`、策略 `is_enable`、群关联 `op` 等字段都保留为 `String`。相关模型的 companion object 提供已知常量，例如 `GroupMember.ROLE_ADMIN`、`GroupJoinRequestApproval.OP_DECLINE`。

原因是这些 v2 群管理页仍在快速演进，且 `QQGuild.DefaultJson` 对未知 enum 值不会自动降级。core 可把已知 `member_role` 映射到已有 `QGGroupRole`，映射不了时返回 `null` 并保留 `memberRoleValue`。这也避免把事件专用的 `GroupMessageAuthorRole` 错当作群管理模型的长期共享类型。

### 3.3 时间、空值与服务端部分响应

低层所有 RFC3339 字段保持 `String?` 或 `String`：官方明确必返才使用非空且合理默认值，其他字段一律可空或给空集合/空游标默认值。core snapshot 在显式的 `@ExperimentalQGApi` 便利属性上才调用现有 `String.toTimestamp()`；解析异常应直接显现，不能吞掉并伪造时间。

创建策略、更新策略、白名单更新的响应只是部分回执，不能错误反序列化为完整策略。分别定义 `JoinApprovalStrategyCreated`、`JoinApprovalStrategyUpdated`、`JoinApprovalStrategyWhitelistUpdated`。`POST .../execute`、审批、禁言、删除策略等仅返回 `Unit`。

### 3.4 不缓存、不猜测、不轮询

- `QGGroup.info()`、`botState()`、`restrictChatState()` 每次调用直接请求；不修改 `QGGroup.name`，因为 `name` 是非挂起属性，读取时发网络请求会违反当前对象语义。
- 成员、申请、黑名单和策略列表是 cold flow/`Collectable`，一遍收集就是一遍新的远端遍历；不缓存上一页。
- `execute` 官方说明约十分钟异步完成且没有状态查询端点。facade 仅命名为 `execute()` 并返回 `Unit`，文档明确它代表“请求已被接受”，不是“所有申请均已审批”。
- 不凭现有 `GROUP_MEMBER_ADD/REMOVE` 事件维护本地成员表；这些事件不是完整成员快照，也无法覆盖首次启动前历史。

## 4. 权限、内邀和数据保护

| 条件 | SDK 行为 |
| --- | --- |
| `11253` 白名单限制 | 保留平台 `QQGuildApiException`，在 core 文档中标注接口前置条件；不改写为 `null`/空列表。 |
| 需机器人为群管理员 | 不预检角色、不额外请求 bot state；直接发目标操作，让平台给出权威结果。 |
| 成员/黑名单“内邀接入中” | API 仍完整实现，core 文档和 KDoc 标注该平台门槛；所有测试默认 Mock，不要求公共环境真实成功。 |
| 申请验证消息、问答答案、`risk_tips`、拒绝理由、白名单 QQ 号 | 不增加日志；KDoc 标为敏感输入。现有 `love.forte.simbot.qguild.api` DEBUG 日志会记录通用 body/response，因此生产环境不得为该 logger 开启 DEBUG。 |
| 黑名单添加 | facade 不自动“先踢再拉黑”：平台规定目标必须已不在群中。批量移除的 `add_to_member_blacklist` 和独立黑名单操作保持两个不同的显式动作。 |

## 5. 兼容性和实现纪律

1. 所有新增 `public` 类型、函数和属性使用多行 `/** ... */` KDoc；内部复杂分页、映射和忽略失败分支也添加简短注释。
2. API 类维持私有构造器、`@JvmStatic create`；需要 lambda DSL 时采用 `@JvmSynthetic`，不能让 Java 看到不友好的 Kotlin 函数类型。
3. 只新增成员或改变 `QGGroup` 目前的占位实现；不删改已有签名，不把现有 `QGGroupMember` 的未获知字段伪造为真实数据。
4. `module-info.java` 导出新增包；JVM API dump 只在代码和 ABI 测试通过后更新。
5. 任何 Live Test 必须从环境变量/本地忽略配置取凭证，默认禁用，输出中不打印 token、secret、验证答案或完整 OpenID 列表。
