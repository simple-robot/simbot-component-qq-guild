# 批次 4：自动审批策略管理器

## 为什么它属于 `QGBot`

策略 API 的资源根是 `/v2/groups/join_approval_strategy`，创建时可一次关联最多 100 个群，且允许以 QQ 群号或群 OpenID 两种互斥形式表示目标。因此它不是某一个 `QGGroup` 的子资源，也不是 `GroupRelation.groups` 的“已加入群列表”。把它挂到 `QGGroup` 会迫使一个策略复制到多个对象，并且无法自然表示 `group_ids`。

本批使用现有自定义菜单/指令面板的 manager + handle + snapshot 形状：远端状态不缓存；无网络的 `handle(id)` 只承载 ID；列表结果才是带 `source` 的瞬时 snapshot。

## 1. 新增公共 API

新增包 `love.forte.simbot.component.qguild.approval`，并在 `QGBot.kt` 增加：

```kotlin
/** QQ 群入群自动审批策略的管理入口。每次读取都不缓存远端策略。 */
public val joinApprovalStrategies: QGJoinApprovalStrategyManager
    get() = QGJoinApprovalStrategyManagerImpl(this)
```

使用复数名称与现有 `customMenus`、`commandPanels` 并列。getter 创建轻量 facade，不发请求；不能存为全局单例，避免把已取消 bot 的协程/认证状态捕获进共享对象。

公共类型与方法如下：

```text
QGJoinApprovalStrategyManager
├─ handle(strategyId: ID): QGJoinApprovalStrategyHandle       # 无请求
├─ create(input: JoinApprovalStrategyCreate): QGJoinApprovalStrategyHandle
└─ list(startCursor?, limit?, autoPagination = true): Collectable<QGJoinApprovalStrategy>

QGJoinApprovalStrategyHandle
├─ id: ID
├─ update(input: JoinApprovalStrategyUpdate): QGJoinApprovalStrategyUpdateReceipt
├─ execute(): Unit
├─ updateWhitelist(input: JoinApprovalStrategyWhitelistOperation): QGJoinApprovalStrategyWhitelistUpdateReceipt
├─ addWhitelistUsers(qqNumbers: Collection<String>): QGJoinApprovalStrategyWhitelistUpdateReceipt
├─ removeWhitelistUsers(qqNumbers: Collection<String>): QGJoinApprovalStrategyWhitelistUpdateReceipt
└─ delete(vararg options: DeleteOption): Unit

QGJoinApprovalStrategy : QGObjectiveContainer<JoinApprovalStrategy>, QGJoinApprovalStrategyHandle
QGJoinApprovalStrategyUpdateReceipt : QGObjectiveContainer<JoinApprovalStrategyUpdated>
QGJoinApprovalStrategyWhitelistUpdateReceipt : QGObjectiveContainer<JoinApprovalStrategyWhitelistUpdated>
```

每个公开类型/方法使用多行 KDoc。KDoc 必须明示：QQ 号码是 string 而非 `ID`，创建时 `groupOpenids/groupIds` 必须二选一，策略实际生效要求机器人在关联群中是管理员，`execute` 是异步扫描。

## 2. 有意不提供的 API

| 不提供的东西 | 原因与替代 |
| --- | --- |
| `handle.get()` / `get(strategyId)` | 官方没有单策略详情端点。不能伪造一个 list + filter 的“详情请求”，因为列表只承诺返回当前生效策略且会额外拉取多页。需要时用 `list()` 过滤。 |
| `awaitExecution()`、进度 Flow、完成回执 | 官方只说约十分钟异步完成，未给任务 ID 或状态端点。`execute()` 成功只表示请求已受理。 |
| 自动策略定时器、启动时重执行 | SDK 不拥有业务审批策略的调度意图；用户应用若需要周期任务，应在自己系统中调 `execute()`。 |
| `QGGroup.autoApprovalStrategy` | 一个策略面向多个群且支持 QQ 群号，归属并不唯一。 |
| 自动将 `List<ID>` 转 QQ 号码 | OpenID 和 QQ 号码是不同标识；转换没有官方接口保证，必须让调用者显式选择 `groupOpenids` 或 `groupIds`。 |

## 3. 内部实现

新增：

```text
internal/approval/QGJoinApprovalStrategyManagerImpl.kt
internal/approval/QGJoinApprovalStrategyHandleOperator.kt
internal/approval/QGJoinApprovalStrategySnapshotImpl.kt
```

### 3.1 manager

```kotlin
@OptIn(ExperimentalQGApi::class)
internal class QGJoinApprovalStrategyManagerImpl(
    private val bot: QGBot,
) : QGJoinApprovalStrategyManager {
    override fun handle(strategyId: ID): QGJoinApprovalStrategyHandle =
        QGJoinApprovalStrategyHandleOperator(bot, strategyId)

    override suspend fun create(input: JoinApprovalStrategyCreate): QGJoinApprovalStrategyHandle {
        val created = bot.executeData(CreateJoinApprovalStrategyApi.create(input))
        return handle(created.strategyId.ID)
    }

    override fun list(...): Collectable<QGJoinApprovalStrategy> = /* cold flow */
}
```

代码实际导入已有 `ExperimentalQGApi` 是因为 `QGBot.executeData` 带该 opt-in；新公共 manager 本身不额外标记为实验性。`create` 只返回 handle，与 `QGCommandPanelManager.create` 的原则相同：创建回执不等于完整策略，不隐式做一次列表扫描来填充它。

`list` 的冷 flow 使用 `GetJoinApprovalStrategyListApi.create(cursor, limit)`，逐项 `emit(record.toSnapshot(bot))`；当 `autoPagination` 为 false 或 `nextCursor.isEmpty()` 时停止。实际请求前才初始化 cursor。不得依据 `isEnable` 再过滤，因为官方列表本身的返回定义由服务端决定。

### 3.2 handle

`QGJoinApprovalStrategyHandleOperator` 持有 `QGBot` 与 `ID`，不持有缓存 record：

```text
update(input)          -> ModifyJoinApprovalStrategyApi(id.literal, input)
execute()              -> ExecuteJoinApprovalStrategyApi(id.literal)
updateWhitelist(input) -> ModifyJoinApprovalStrategyWhitelistApi(id.literal, input)
delete(options)        -> DeleteJoinApprovalStrategyApi(id.literal)
```

`addWhitelistUsers` 和 `removeWhitelistUsers` 是唯一允许的便利封装：分别构造 `JoinApprovalStrategyWhitelistOperation(OP_ADD, qqNumbers.toList())` / `OP_DEL`。它们不切分超过 10000 的输入，防止一次调用被无声拆成多次而造成部分成功语义不透明。

删除实现沿用 `QGCommandPanelHandleOperator.delete`：默认错误上抛；只有调用方传入 `StandardDeleteOption.IGNORE_ON_FAILURE` 才使用现有 `runCatchingCancellable`，并以不含敏感数据的 debug 文本记录失败。不要自行定义另一套 delete option。

### 3.3 snapshot 与回执

`QGJoinApprovalStrategySnapshotImpl` 通过委托 `QGJoinApprovalStrategyHandle by QGJoinApprovalStrategyHandleOperator(bot, source.strategyId.ID)` 获得动作；它只投影 source 已有字段：

```text
id, groupOpenids, groupIds, whitelistUserCount,
isEnabledValue, expiresAt, createdAt, updatedAt, remark
```

`isEnabledValue` 保留 `String`；可另给 `isEnabled: Boolean?`，只在 `on -> true`、`off -> false` 时返回值，未知返回 null。不要把过期时间、`on/off` 或白名单数量缓存到 handle，也不要因为 update 回执返回了新状态就篡改已存在 snapshot 的 `source`。

三个回执分别围绕低层回执构造：

```text
QGJoinApprovalStrategyUpdateReceipt
├─ isEnabledValue
└─ expiresAt

QGJoinApprovalStrategyWhitelistUpdateReceipt
├─ strategyId
├─ whitelistUserCount       # 官方称估算值
└─ updatedAt
```

没有创建回执 wrapper：manager 复制当前 `QGCommandPanelManager` 约定，只返回 ID handle。使用者若想保留创建时的 `isEnable/expireAt`，可在业务层自己保存 input 或直接调用低层 API。

## 4. JPMS、文档和 Java 互操作

1. 在 core `src/jvmMain/java/module-info.java` 增加 `exports love.forte.simbot.component.qguild.approval;`；内部包绝不 export。
2. `QGBot.joinApprovalStrategies` 是公开二进制 API，生成/检查 core api dump；不得把它设为 extension property，避免 Java 和二进制 API 不可见。
3. `handle`、`create`、`list`、`update`、`execute`、白名单方法均保留普通成员函数，供 Java 调用。只在后续确有成熟 builder 后才另加 `@JvmSynthetic` Kotlin DSL，当前不引入 lambda-builder 双接口。
4. 完成后更新 core README 的能力说明或手册索引，写清策略是“群入群自动审批策略”，不是频道成员管理或消息按钮。

## 5. 测试场景

在 core commonTest 新增 `QGJoinApprovalStrategyManagerTests.kt`，用 MockEngine 覆盖：

1. 访问 `bot.joinApprovalStrategies` 和 `handle(id)` 不请求网络。
2. `create` 仅 POST 并返回指定 ID handle；不在创建后 GET/list。
3. `list` 是冷集合，`autoPagination` 真正控制第二页，请求带 cursor/limit。
4. update 为 PATCH；delete/execute 无 body；execute 的测试名称避免出现 `complete`、`await`。
5. 白名单 add/del 均把号码序列化为字符串数组，回执的计数和时间正确映射。
6. delete 默认抛异常，`IGNORE_ON_FAILURE` 吞掉可恢复异常但不吞 coroutine cancellation。

Mock 测试只验证 core 到低层 API 的委派。真实联调仍需机器人拥有策略相关权限、至少一个管理员关联群；没有该条件时将“策略真正运行”记录为未验证，不能凭 HTTP mock 宣称完成。
